# Judging walkthrough

Run `make demo`. Keep the storefront, `/staff`, `/benchmarks` and a terminal open beside one another. Use fictional customer aliases. Everything persists locally. Default staff key is `local-demo-staff`.

1. **Before launch:** On `/staff`, close reservations if already launched. In the storefront enter `Judge-A`, choose Cloud hoodie size L, quantity 2, and save interest. Show the real size-level demand summary on both pages.
2. **Launch:** In staff controls click Launch drop. Reserve one hoodie from the storefront. Open the digital receipt, identify the actual scan code, read the countdown and download the reserved Story PNG.
3. **Real concurrency:** On `/benchmarks` select **One online unit · race**, 100 requests, concurrency 100. Click Run or execute `make bench SCENARIO=race REQUESTS=100 CONCURRENCY=100`. Show one successful hold, 99 expected conflicts and all three invariant checks. No values appear before an actual run.
4. **Protect the floor:** Run `five` (three unique holds from five units) and `floor` (no online holds from two). In staff inventory find a regular variant with two available units after reserving surplus. Scan one of those units, start fitting and checkout the returned fitting hold ID. Walk-in purchase can consume protected units.
5. **Display rule:** Scan `DR02-M-06` (or another available `-06` display unit). Start fitting. Make online reservations for that size concurrently; its display unit is never allocated online. Checkout uses the fitting hold already created. For a separate available display unit, confirm stockroom placement and tick Publish surplus online to explicitly publish it.
6. **Who wins first:** An online-held scan code is rejected by Start fitting. If fitting wins on an available unit, a subsequent online reservation can only select other eligible units above the floor. `make test` checks both orderings and a simultaneous displayed fitting/checkout race.
7. **Fitting overdue:** Start another fitting and wait 30 seconds. Show the overdue alert and that unit still marked `fitting`. Confirm physical return and show it becoming available exactly once. Trying Return again gets a state conflict.
8. **Duplicate request:** Run `duplicate`. Explain that 100 identical successful HTTP responses replay one hold and receipt. Use the unique hold count and staff scan ledger to distinguish successful requests from allocated stock.
9. **FIFO / release:** Reserve all surplus of an ordinary variant, join the waitlist as two aliases, then let the 120-second online holds expire. The worker releases once, offers eligible surplus in FIFO order for 20 seconds, and the first alias can Claim offer. Keep only one unit of surplus for a visually simple sequence. If fitting consumes another available unit before expiry, the release may leave just two units and no offer should be created.
10. **Reminder / directions:** Keep an online hold active until 110 seconds after reservation. Check the alias inbox for the reminder, illustrative ground-floor directions and request to bring the digital receipt. Edit the reminder draft before the reminder window to demonstrate controlled copy.
11. **Pickup versus expiry:** Checkout one existing online hold before its deadline, then let the clock pass. It stays sold. An already expired online hold rejects checkout. Tests also issue pickup/expiry concurrently and verify one terminal state.
12. **Worker recovery:** Pause worker processing in staff controls, let a hold pass expiry, and show stock remains held. Resume processing: one sweep recovers the release. `make test` additionally starts, stops and restarts a real Asynq worker and verifies recovery. Worker heartbeat and pending outbox are visible in benchmarks.
13. **Social import:** Click Scrape synthetic social site in `/staff`; show the bundled page with captions, comments and hashtags. The hoodie receives one baseline post and five current posts; unrelated weather content stays unmatched. Scrape again and show zero newly imported posts. Storefront shows a labelled Trending Drop. Reach and engagement are synthetic fixture values, not live Instagram analytics.
14. **Collection:** Checkout an existing fitting/online hold, return to the alias's receipts, and download the collected Story PNG. It is a personalised 1080×1920 canvas image. Download receipt JSON, benchmark JSON and request CSV.

The automated acceptance checks execute these state transitions without waiting two minutes, by setting test-database deadlines in fixtures. They never accelerate deadlines in the running application. Run `make test` for the complete automated matrix and Go memory-race checks.

For longer visible live charts, use a bounded longer run such as `make bench SCENARIO=race REQUESTS=3000 CONCURRENCY=50`. The dashboard samples twice per second and reconnects if its stream breaks. Leave runs shorter than the hold duration when demonstrating a fixed unique-winner count. Benchmark fixtures are retained for auditing and add physical units to instance totals.
